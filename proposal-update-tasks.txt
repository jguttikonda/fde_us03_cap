PART 1.  WHAT WE DECIDED (read this first, 2 minutes)
====================================================================================================

  1. We are NOT sure the design is "A2A" (agent-to-agent) or "agent + sub-agent". So we stop saying
     A2A. Use the neutral words "multi-agent" until the team decides.

  2. The Report Creation Agent is removed. Final reporting becomes a DETERMINISTIC (rule/template
     based) task that belongs to the Controller Agent. There is no report-creation agent file.

  3. The Inventory Agent is a SUB-AGENT of the Maintenance Agent. Maintenance calls it, Inventory
     answers Maintenance. Inventory does not talk to the Controller directly.

  4. The Maintenance Agent has one job: establish an ETA (when can the aircraft fly again?) and,
     based on that ETA, give risk metrics. It does not "check work-order completeness" as a
     deterministic rule.

  5. The Controller's deterministic rules are described ONLY in controller-agent-proposal.md. The
     main proposal just points to that file (no duplicate copy).

  6. Sections 9, 10, 11, 12, 13 of the main proposal stay, but are tagged OPTIONAL / GOOD TO HAVE.

  7. Operations Agent covers BOTH flight disruption AND package (cargo) disruption, and its file
     gets a use-case scenario with mock data.

PART 2.  AGENT MAP AND HANDSHAKES (used by every task below)
====================================================================================================

  Based on the main architecture diagram (Section 5), updated for the decisions above.

  Final agent list:
    - Controller Agent   (top level; also builds the final report deterministically)
    - Maintenance Agent  (top level; owns the ETA and risk metrics)
    - Inventory Agent    (SUB-AGENT of Maintenance)
    - Operations Agent   (top level; flight + package disruption)

  Diagram (paste-ready Mermaid for Section 5 and Section 7.1):

    flowchart TB
        Human[Human] -->|AOG event| Controller[Controller Agent]
        Controller -->|repair ETA request| Maintenance[Maintenance Agent]
        Maintenance -->|part check request| Inventory[Inventory Agent - sub-agent]
        Inventory -->|availability and lead time| Maintenance
        Maintenance -->|ETA and risk metrics| Controller
        Controller -->|ETA window and options| Operations[Operations Agent]
        Operations -->|flight and package impact| Controller
        Controller -->|ranked recommendation report| Human
        Human -->|approve or reject| Controller

  Handshake table (use these IDs and names everywhere so the files match):

   ID  | From           | To             | What is passed
   ----+----------------+----------------+-----------------------------------------------------------
   H1  | Human          | Controller     | AOG event: aircraft id, fault, station
   H2  | Controller     | Maintenance    | Validated event + defect context. Ask: repair ETA
   H3  | Maintenance    | Inventory      | Required part numbers, station, need-by time
   H4  | Inventory      | Maintenance    | Stock per station, alternates, supplier lead time,
       |                |                | parts-ready ETA, confidence
   H5  | Maintenance    | Controller     | Return-to-service ETA, risk metrics, confidence, assumptions
   H6  | Controller     | Operations     | Event + ETA window(s) + candidate recovery options
   H7  | Operations     | Controller     | Affected flights, affected packages, swap options,
       |                |                | recommended operational path, confidence
   H8  | Controller     | Human          | Ranked recommendation report (built by deterministic rules)
   H9  | Human          | Controller     | Approval or rejection

  Standard heading every agent file must use for its handshake section (so files look the same):
        ## 2A. Handshake with Other Agents
      with four short lines: Agent type (top-level or sub-agent) / Called by / Calls / Payload in and out
      (reference the H-numbers above).

PART 4.  HOW TO WORK (so four people can edit one file without breaking each other)
====================================================================================================

  1. Start from the latest proposal_draft:    git switch proposal_draft ; git pull
  2. Make your own branch, for example:       git switch -c update/<your-name>
  3. Edit ONLY the sections named in your tasks. Commit small and often.
  4. One PR per person into proposal_draft. Use your task IDs in the PR title (e.g. "T02 T04 T10 T15").
  5. Before opening the PR:  git pull origin proposal_draft  and fix any conflicts.
  6. propsal.md is touched by several people. To limit conflicts, merge in this order:
        Phase 1 (removals):   Preet (T02, T04, T15), Jag (T03), Sri (T01)
        Phase 2 (rewrites):   Sri (T05, T06, T09), Jag (T07, T11, T12), Preet (T10), Jay (T13, T14)
        Phase 3 (finishing):  Jay (T08, T16)
     If two PRs touch the same lines, the later PR resolves the conflict, not the earlier one.
  7. Do not delete content that is not listed in your task. If something looks wrong, add a comment
     in your PR instead of silently changing it.

  Overlap rules (these places are touched by more than one task, so ownership is fixed):
     - Section 1 Executive Summary, first paragraph ........... Sri (T01) edits the WHOLE paragraph
                                                                 (A2A wording AND the agent list).

     - Section 7 heading numbers ................................ Jag renumbers after T07.
